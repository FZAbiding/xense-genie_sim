# 固定底盘在线 IK：同步误差日志与 Pinocchio A/B

本阶段基于 `1fffdf5` 开发。目标是把“误差来自哪里”和“换模型改善了什么”变成可核查实验，**不修改原 QP 控制律，不解锁底盘，不宣称已实现实测状态笛卡尔闭环**。

## 1. 本阶段开发了什么？

1. `--kinematics-backend urdf|pinocchio`：可选在线模型后端，默认仍是 `urdf`。
2. `control_ticks.jsonl`：同一控制观测周期保存目标、最后发布命令、反馈关节状态与三套 EEF。
3. `analyze-ticks`：位置误差向量分解、时间指标和曲线，失败轨迹也保留并标记 partial。
4. `verify-ticks`：用独立 URDF FK 对抽样快照中的关节与位姿重新计算，避免只检验代数恒等式。
5. `batch`：固定世界变换，多 episode、双后端、交替重复顺序；保留失败与未执行项。
6. `batch-evidence`：导出可本地打开的 Web 验收页、图、CSV 和带输入哈希的 JSON。

本次在线实验使用原有 Pinocchio 4.1.0 隔离 venv；没有向基础 `xense-wbc` 安装 Pinocchio，也没有改动 PhysX/ROS 的系统依赖。
可选后端的导入、模型构建和 MoveIt FK 对照在首帧实际运动前执行；失败不会静默退回 URDF 后端。

## 2. 同周期快照的合同

### 保存了哪些内容？

| 字段 | 含义 |
|---|---|
| `tick / source_time_s` | 控制周期编号与源目标相位 |
| `observation_*_time_s` | 控制器观测时的 ROS / 单调 / 墙钟时间 |
| `feedback.sequence` | 本进程收到的反馈消息序号 |
| `feedback.sample_ros_time_s` | JointState 消息携带的采样时间戳，不自行伪造 |
| `feedback.receive_*` | 收到回调时的时间，区分于采样时刻 |
| `last_publication` | 最后一次位置命令的本地序号、消息时间戳、发布完成时间 |
| `positions_measured / velocities_measured` | 该反馈消息的关节位置/速度，按关节名保存 |
| `positions_last_command` | 最后发布命令对应的模型配置 |
| `eef_target / eef_measured / eef_last_command` | 当前目标、反馈 FK、命令 FK，统一在 odom、统一指尖 TCP 定义 |

目前控制器采用同一个 ROS executor 顺序回调。快照在本周期发送新命令前取得，并在碰撞服务可能处理后续反馈之前落盘。
即使本周期随后因跟踪保护或 QP 失败停止，已经取得的最后观测仍保留，而不是只记录成功命令。

### 重要边界：发布不等于驱动确认

`last_publication` 是控制器最后发出的命令，**不是执行器返回的“当前已应用命令”确认**。
ROS 消息可能仍在传输，反馈也可能比最后一条命令更早。因此这里得到的是明确的、可重算的**命令相对位置差**，不是已经独立识别的执行器时延或纯机械伺服误差。

```text
目标 - 反馈 FK
  = (目标 - 最后发布命令 FK) + (最后发布命令 FK - 反馈 FK)
          task                         following
```

这是位置向量恒等式。三个范数、P95 不能直接相加，也不能拿两项范数比例当成因果贡献率。
旋转不按这个简单向量加法分解；日志保存了四元数，后续可单独做 SO(3) 残差分析。

`callback_age` 是观测时刻减收到回调的时刻；`message_stamp_age` 是 ROS 时钟下观测时刻减反馈消息时间戳。
后者只有在消息戳有效且时钟一致时才可解释；两者都不等于完整传感—控制—驱动时延。

## 3. A/B 的实验协议

- 固定底盘、固定头部，腰＋双臂＋夹爪主关节共 21 个命令变量。
- 同一 QP 任务、权重、关节/机构约束与位置驱动；没有为了 Pinocchio 调大容差或关闭碰撞检查。
- 同一隔离 Python 环境运行两个后端，避免把不同解释器/包版本当成模型差异。
- 从旧 v5 `run-001` 冻结**一个** `world_to_odom`，保存为本批 `fixed-world-config.json`。
- 不按 episode 各自重新居中，不分别旋转双手，不缩放动作。
- 把限速配置复制为本批 `limits-profile.json`，各运行使用同一快照。
- 先对 000/001/002 的两个后端做首帧无运动预检；这只是首帧预检，不能替代完整轨迹验收。
- 正式协议是 3 个 episode × 2 后端 × 2 重复，共 12 项；第二轮反转后端顺序，减小固定先后顺序影响。
- 保持 30 Hz、源时钟 1× 和已知文件的一帧前瞻；**不是无前瞻因果 VLA 实验**。
- 执行中任一失败或超时，整批停止，不从未知停止姿态偷偷继续后面的实验；剩余项保留 `not_run`。

新增同步日志本身有计算/写盘成本，因此本批与历史 v5 也不是严格的单因素耗时对照；应比较本批两个都开启日志的后端。

### 尚不具备的严格控制条件

探索批次的首帧仍由 BioIK 分别求解，初始物理反馈/回零偏差也可能不同，所以不能声称每对实验具有完全相同的 IK 分支和物理初态。
每次保存 `initial_measured_positions_rad`、`initial_approach_goal_rad`；导出页的 JSON 给出同 episode、同重复序号的最大腰/臂角差。

这是在线**试验性 A/B**，可检查是否能运行、计算预算、硬约束与观测误差是否明显退化；
不是足以把亚毫米精度变化归因于后端的严格统计实验。进一步精度比较需要复用验证过的首帧关节解、规范复位与更多重复。

实际发现第一轮各 episode 的首帧腰/臂关节解最大差约 1.043 / 0.873 / 2.129 rad，远大于初始反馈差约 0.002 rad。
因此又增加 `--approach-reference-batch`，让每个 episode 的两个后端复用探索批次 URDF/r01 的同一首帧关节解，重新检查原生/机构约束、EEF 残差和完整接近路径碰撞。
不是直接把机器人传送到保存的关节角，也不是跳过碰撞验证。

固定首帧解的批次使用新启动的仿真场景，避免从探索批次中途停止的姿态继续。真实反馈仍存在小差异；固定目标解不等于精确重置所有物理状态。

### 固定同一首帧关节解：实际 6 项运行结果

以下每个 episode 的两个后端首帧目标关节配置逐项完全相同；均完成就位、回放和回零，但**不是所有命令约束验收都通过**。

| episode / 后端 | 命令数 | 超时 | IK P95 | 周期 P95 | 左/右 total P95 |
|---|---:|---:|---:|---:|---:|
| 000 / URDF | 1250 | 0 | 4.917 ms | 14.506 ms | 10.462 / 7.962 mm |
| 000 / Pinocchio | 1250 | 0 | 2.450 ms | 10.793 ms | 10.470 / 7.737 mm |
| 001 / URDF | 1032 | 0 | 4.811 ms | 14.048 ms | 11.608 / 8.794 mm |
| 001 / Pinocchio | 1032 | 0 | 2.486 ms | 10.658 ms | 11.317 / 8.656 mm |
| 002 / URDF | 1238 | 1 | 4.695 ms | 13.738 ms | 12.096 / 10.513 mm |
| 002 / Pinocchio | 1239 | 0 | 2.464 ms | 10.817 ms | 11.679 / 10.244 mm |

计算预算得到改善，但不是 11 倍整链提速，也没有把厘米级跟踪差自动消掉。样本仍少，不能把表中小幅精度差当作有统计意义的因果结论。

002 / URDF 在源相位 38.001 s 有一次 deadline miss，原执行策略发 HOLD 并继续，因此报告运行完成；旧命令审计明确标为加速度不完整。
本轮新增 HOLD 转换审计，把这一周期作为零推进命令重建：`idx05_body_joint5` 的名义加速度为 `3.545367 rad/s²`，配置是 `3 rad/s²`，超过约 `0.545367 rad/s²`。
用实际已发布位置序列重新差分，得到相同超量。**这不是物理电机加速度测量，但已证明该名义命令连续性未达标。**

因此验收页给出 `not_fully_passed`，保留原执行报告，不将其改写成全绿。
新增批测器遇到 HOLD 补充审计失败会停止后续任务；控制器本身的超时平滑降级和速度状态连续性尚未修复。

### 探索批次第一对：保留历史口径

探索批次第一对 episode 000 / repeat 1，实测结果如下，**首帧关节解不同，不能当作严格的后端精度比较**，也不是全部重复的平均结论：

| 指标 | URDF | Pinocchio |
|---|---:|---:|
| 整个命令周期 P95 | 13.981 ms | 11.225 ms |
| 左手 total 位置 P95 | 10.188 mm | 11.373 mm |
| 左手 task 位置 P95 | 0.185 mm | 0.242 mm |
| 左手 following 位置 P95 | 10.218 mm | 11.253 mm |
| 右手 total 位置 P95 | 7.848 mm | 8.597 mm |
| 右手 task 位置 P95 | 0.172 mm | 0.228 mm |
| 右手 following 位置 P95 | 7.824 mm | 8.654 mm |

可以支持的解释：该对运行中，较大的总位置差主要呈现在“相对最后发布命令的反馈位置差”这一几何量中，命令相对当前目标的残差较小。
但不能据此断言“驱动 PD 占误差 98%”，因为还混有时间对齐和命令应用状态未知等因素。

也不要说“Pinocchio 必然更准”：这一对的 total P95 反而略大，同时命令周期更短。
换模型能节约计算预算，不等于已经改好驱动跟随或上层闭环。

### 独立快照重算

第一条 Pinocchio 在线运行抽样 100 个 tick，独立 URDF FK 重算已记录的反馈/命令位姿，最大位置差约 `1.923e-15 m`。
它证明关节快照与已记录位姿对应，**依然不是物理定位精度**，也不替代驱动确认。

### 探索批次发现的真实失败：关节制动可行性

12 项计划中，9 项完整回放并回零通过；episode 001 / URDF / repeat 2 在源相位 28.234 s 拒绝继续，余下 2 项未执行。
失败前有 847 条命令，最后一个失败观测也留下来，共 848 条快照。不是将中途停止算作轨迹成功。

快照及上一条命令可精确重算出：

```text
关节：idx01_body_joint1
命令位置：0.0001 rad，已到其上限
上一命令速度：+0.100672977 rad/s
配置加速度：3 rad/s²；名义周期：1/30 s

加速度边界要求：下一速度 >= 0.100672977 - 3/30 = +0.000672977 rad/s
位置边界要求：下一速度 <= 0 rad/s
两者无交集，按原逻辑停止。
```

这不是 Pinocchio 的 FK 精度问题，也不能靠放宽 `1e-7` 判据掩盖。
当前 QP 只约束下一步位置，没有保证“到达下一步后还有足够制动余量”；像车开到墙边才开始要求刹车。
本轮加入回归测试，确保这种状态被拒绝，不静默裁剪后当作成功。**尚未实现通用制动可行域修复**。

下一步应设计与当前离散积分一致的速度可行包络/制动余量，并考虑机构耦合。
连续近似 `v²/(2a)` 可帮助理解停车距离，但不能不加推导直接当作当前离散位置命令的严格安全保证；物理驱动制动还需另测。
该失败与后续固定首帧解批次都保留，后者通过也不能抹掉这个控制器限制。

## 5. 本机复跑入口

先启动既有固定底盘仿真与 MoveIt。以下命令从仓库根目录执行，**默认 batch 没有运动；加 `--execute` 才实际执行**。
不要同时在 Web 点击播放；进程间命令租约仍会拒绝竞争控制器。

```bash
mamba activate xense-wbc
source devel/setup.bash
export ROS_DOMAIN_ID=42 OPENBLAS_NUM_THREADS=1

wbc_demo/logs/wbc-next-stage/pinocchio-venv/bin/python wbc_demo/umi_demo.py batch \
  --reference-run wbc_demo/logs/umi-realtime-web-reliable-01/run-001 \
  --approach-reference-batch wbc_demo/logs/wbc-online-ab-20261019-01 \
  --episodes 0 1 2 --repeats 2 \
  --output wbc_demo/logs/my-online-preflight
```

确认首帧结果后，使用**不同的输出目录**并显式加 `--execute`。输出目录必须不存在，不能覆盖旧结果。
需要一次只测一个后端时用 `--backends urdf` 或 `--backends pinocchio`。

```bash
python wbc_demo/umi_demo.py analyze-ticks --run-directory <具体运行目录>
python wbc_demo/umi_demo.py verify-ticks --run-directory <具体运行目录> --samples 100
python wbc_demo/umi_demo.py batch-evidence \
  --batch-directory <批次目录> --output <新的验收目录>
```

单次回放也支持：`replay --playback-mode realtime --kinematics-backend pinocchio ... --execute`。
Web 的 `live` 启动参数同样支持 `--kinematics-backend`，会传给真实回放子进程；不是只改界面标签。当前没有新增后端切换下拉框。

## 6. 下一步开发与学习

1. 优先补离散制动可行域、接近限位与机构耦合的回归实验；不要把这次已复现失败留给更激进的闭环增益。
2. 根据同周期日志做静态保持与受控扰动，区分动态滞后、稳态偏差和模型差异。
3. 引入明确的反馈/目标时序、有效命令确认或可验证的传输合同，再设计实测状态笛卡尔闭环。增益独立于控制周期，处理噪声、暂停/恢复，不是直接替换 `positions`。
4. 单独做无前瞻目标流与中断保护，不把文件前瞻冒充实时 VLA。
5. 固定底盘阶段通过后，再决定轮式运动学或力矩 WBC 分支。

建议重点学习：闭环误差方程、采样与延迟、任务空间速度前馈、约束可行性。
当前证据更支持先理解并改善反馈/执行链，而不是继续追求更小的 FK 浮点差。
