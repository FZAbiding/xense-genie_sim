# 为什么以前慢？怎样做到原速在线全身 IK？

**当前状态：慢放与三视图传输空档均已修复并完成本轮验收。直接查看 [v5 同目录视频/图片](media/episode-000-v5/index.html)，最新实测见第 7 节。早期失败与暂停记录保留在第 6 节。**

## 1. 先纠正之前的表述

之前的 Web 页面是**在线查看仿真**，不是**逐帧在线求 IK**。这两件事不能混用。

旧模式会先用 MoveIt 2 + BioIK 求出全部关键帧关节角，检查插值路径，再慢速执行。
原始 episode 000 是 1250 帧、30 fps，即 **41.6667 秒**；v4 实测执行约 **933.97 秒**，约慢 22.4 倍。
不能用离线四分屏 MP4 的 41.67 秒时长来证明当时控制实时：那个 MP4 是按源相位重新采样的。

慢放的来源不只是前端：

1. CLI 的旧默认 `--speed 0.5`，本来就要求至少慢两倍。
2. `execution.retime()` 用所有关键帧中最严格的一段计算**全局**时间倍率。
3. 每段三次插值都按段首、段尾速度为零来限加速度，相邻密集关键帧反复“刹停再启动”。
4. 腰、双臂、夹爪都套用旧的 `0.3 rad/s`、`0.5 rad/s²` 演示限速；一次快速夹爪变化也能拖慢整段。
5. 旧执行时钟每次最多累加 40 ms，计算卡顿还会进一步拉长播放。
6. 源视频跟随这个慢速控制相位；JPEG 预览至多 12.5 Hz，浏览器图片轮询又至多约 10 Hz。

因此**只把 `--speed` 改成 1，或者只让视频快进，都不是修复**。

## 2. 新旧两个模式

| 模式 | IK 在什么时候计算 | 时间策略 | 用途 |
|---|---|---|---|
| 在线 IK / `realtime` | 每个控制周期重新计算双手与腰部的联合微分 IK | 单调墙钟 1×，目标 30 Hz，不全局重定时 | 原速仿真回放 |
| 安全慢放 / `validated` | 运动前求全部关键帧，再插值执行 | 按旧保守限速全局重定时 | 与 v4 对照、慢速检查 |

Web 默认选择新模式；直接调用 CLI `replay` 仍默认旧模式，避免悄悄改变已有自动化命令。
Web 中可以手动切回旧模式。底盘依然固定，头部关节不参加 IK；腰部 5 自由度、双臂 14 自由度参加联合求解，
另有 2 个夹爪主关节一起受限，跟随关节按 URDF mimic 更新。

### 时间到底如何对齐？

```text
首帧求解和安全就位（源视频停在第 0 帧，不计入 41.67 秒）
    ↓
启动同一个源相位时钟 t = 当前 monotonic 时间 - 开始时间 - 暂停时间
    ├── 原生 <video>：直接播放数据集 H.264 MP4，playbackRate = 1
    ├── 在线 IK：读取该相位附近的原始双手 EEF / 夹爪目标，现算现发
    └── 三个机器人镜头：真实 PhysX 反馈经 ROS/渲染获得，MJPEG 推送到浏览器
    ↓
41.67 秒源片段结束，再安全回到本次启动时姿态（不计入源片段时长）
```

暂停会冻结 IK 源相位和源视频；恢复扣除暂停时间。
若某一周期晚了，不把过期目标排成长队，也不拖慢源视频；跳到当前相位，并记录超时/跳帧。
连续三次命令周期超时会停止并保持，不用“仍然播放”掩盖控制跟不上。

浏览器源视频使用原始文件和 HTTP Range，不再用每秒十张 JPEG 模拟视频。
三个机器人视图使用“只保留最新帧”的 MJPEG，不保证每张渲染图都不丢帧。
视频时钟与源相位超过 120 ms 时浏览器会纠偏；这不是硬件触发级同步。

## 3. 新模式用的是什么 IK？

**不是 Pinocchio，也不是智元闭源 SDK。**

- 首帧的大范围姿态求解仍使用已有的 **MoveIt 2 + BioIK/GenieBioIK 插件**。
- 首帧到位后，周期内改用本仓库新增的 **URDF Jacobian + 有约束微分 IK + OSQP**。
- 这部分是本次编写的实验代码：`differential_ik.py`、`realtime_execution.py`，不是调用某个官方实时 WBC demo。
- OSQP 是二次规划求解器，不是机器人 IK 库。机器人几何、Jacobian、目标、约束和时钟由仓库代码组织。

### 用“端托盘走一步”理解微分 IK

位置 IK 像问：“整个人最终该摆成什么姿势？”微分 IK 像每隔 1/30 秒问：

> 下一小步，腰转多少、肩动多少、肘动多少，才能让两只夹爪一起接近目标？

Jacobian `J` 表达“小量关节变化如何造成 EEF 的位置和朝向变化”。
每一步求关节速度 `v`，近似满足 `J v ≈ EEF 期望速度`，再积分 `q_next = q + v / 30`。
两只手的任务写进**同一个**优化问题，共享腰部变量，不能拆成两个互不沟通的单臂 IK。

实现包含：

- 夹爪 EEF 随开度变化的指尖中点 TCP，及其对主关节变化的导数；不是法兰 IK 冒充 EEF IK。
- 关节位置、速度、离散加速度边界；腰部/腕部原有线性机构耦合约束。
- 软直腰偏好；选择“直腰对照”时还保留 roll ±0.5° 的硬边界。
- 每个待发送命令的中点、端点，都通过 MoveIt 碰撞/状态有效性检查。
- 用实际 PhysX 关节反馈计算当前 EEF 误差，监控底盘漂移、反馈新鲜度、夹爪误差和命令发布者竞争。
- 启动时本地 URDF FK 必须先与 MoveIt FK 一致，否则不进入在线回放。

它仍然是**位置命令层的运动学 IK**：上一条命令热启动，PhysX 关节驱动跟踪，反馈用于监控和停止。
没有实现力矩级 WBC、接触力分配、动态平衡，也不是带完整避障梯度的笛卡尔伺服器。
碰撞检查是离散中点/端点检查，不是连续扫掠体积证明；场景也没有从 UMI 重建可抓取的方块与箱子。

## 4. 为了原速，是否修改了限速？

**是，而且是单独、公开的仿真配置，不是把旧保护偷偷关掉。**

`configs/g2_realtime_limits.json`：

| 部位 | 规划速度上限 rad/s | 规划离散加速度上限 rad/s² |
|---|---:|---:|
| 腰部 | 0.6 | 3 |
| 双臂 | 1.2 | 8 |
| 夹爪 | 1.8 | 30 |

速度还会与各关节原生 URDF 上限取最小值。位置、耦合和碰撞保护没有关闭。
这些数值仅用于固定底盘仿真实验，**不是经过厂商认证的真机速度/加速度**。
`command_joints.csv` 可独立检查规划离散约束，但不能据此宣称实际电机加速度或操作系统调度经过认证。

夹爪在原速快速开合时存在驱动滞后。当前对**已知的回放轨迹**采用最多一帧（33.3 ms）的目标前瞻，
提前计算下一帧的位姿和开度以补偿部分命令/驱动延迟；实际误差仍对**当前**源相位统计，不拿未来目标做验收替身。
这是已知文件回放，不意味着能够预知在线传感器的未来。无前瞻配置为 `lookahead_seconds: 0`。

## 5. 如何启动与核查

```bash
mamba activate xense-wbc
export OMNI_KIT_ACCEPT_EULA=YES
bash wbc_demo/run.sh umi-web
```

打开 `http://127.0.0.1:8765`，选择“在线 IK：原速 1× / 30 Hz”，点击播放。
如果服务已经运行，不要重复启动，刷新网页即可。

仅控制已有的仿真/MoveIt 后端：

```bash
bash wbc_demo/run.sh umi replay \
  --input wbc_demo/data/converted/episode-000.json \
  --output wbc_demo/logs/my-realtime-run \
  --playback-mode realtime --posture-policy soft --execute
```

`--speed` 仅用于旧模式；在线模式固定源 1×，不会因为该参数重新慢放。

每次运行保留：

- `report.json`：通过/失败、模式、限速、前瞻、源时长/实际时长、命令数、超时数、求解耗时。
- `realtime.csv`：每个周期的源相位、求解/周期耗时、实际 EEF/夹爪误差和腰 roll。
- `command_joints.csv`：21 个命令关节的位置和规划速度，可独立审计限位/速度/离散加速度/机构耦合。
- `command_phase.csv`：源相位与命令 ROS 时间对应关系，用于视频核查。
- `joint_trace.csv`：原始实际关节反馈；同级 `run-NNN.log` 保留异常和失败原因。
- `recording-NNN/`：三路真实渲染视频及图像 ROS 时间戳，不是求解器的 FK 动画替代品。

生成统计图：

```bash
bash wbc_demo/run.sh umi analyze \
  --input wbc_demo/data/converted/episode-000.json \
  --run-directory wbc_demo/logs/my-realtime-run
```

## 6. 验收边界

目标是**本机实测的 30 Hz 软实时仿真回放**，不是“任何机器、任意轨迹都能硬实时”。
一次通过只证明该 episode 在该次运行中达标。快回放与慢回放的跟踪误差不能混作同一成绩；
浏览器原生视频帧率、控制频率、渲染频率也是三个不同指标。

## 7. 当前已完成：图像传输修复与 v5 可视化验收

### 根因与最小修复

图像发布者是 RELIABLE，原 Web 接收端却使用 BEST_EFFORT。对相同三路 640×480 图像做只读 A/B 实验，各运行 6 秒：

| 接收方式 | 各路收到帧数 | 完整三视图束帧 | 最大束帧间隔 |
|---|---|---:|---:|
| BEST_EFFORT | 63 / 56 / 61 | 35 | 966.6 ms |
| RELIABLE | 179 / 179 / 176 | 176 | 42.1 ms |

依据实测，把 Web 图像订阅改为 `RELIABLE`、队列深度 `3`。没有修改内核网络参数，没有动其他工作区任务，也没有重建整个渲染器。
完整记录：`wbc_demo/logs/umi-realtime-work/qos-probe.json`。额外单测固定这一接收契约，防止退回 BEST_EFFORT。
