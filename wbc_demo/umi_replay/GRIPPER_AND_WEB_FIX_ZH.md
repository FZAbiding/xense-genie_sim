# 夹爪开合与 Web 交互修复（v4）

## 1. v3 为什么夹爪不动？

此前是实现限制，不是 UMI 没有开合数据：转换器已保存 `gripper`，但执行器只发布腰部/双臂，
并要求夹爪保持机械零位开启，以维持固定 TCP 假设。现在已取消该限制。

按你给出的语义：**归一化 0 = 闭合，1 = 开启**，不反向、不把归一化值直接当弧度。

| 归一化开度 | 主动关节目标 | 含义 |
|---|---|---|
| 0 | -0.91 rad | 模型原生闭合端点 |
| 0.5 | -0.455 rad | 模型关节行程一半 |
| 1 | 0 rad | 模型原生开启端点 |

主动关节是 `idx31_gripper_l_inner_joint1`、`idx71_gripper_r_inner_joint1`。
其他连杆按 URDF mimic 的 multiplier/offset 联动；执行器只发送两个主动关节，不与 mimic 约束争夺控制。
它们与腰部、双臂使用同一个 `/joint_command` 发布器，保留控制权/反馈/底盘漂移检查。

这是 **URDF 关节行程的线性映射**，不是经过硬件标定的毫米开口映射。
连杆机构使实际间距与角度非线性；如需“源 40 mm 对应机器人 40 mm”，还需要两种设备的开口标定。

端点补测还发现：原生 q=-0.91 时，两侧指垫碰撞网格各有约 **0.195 mm** 交叠，旧 MoveIt 因而拒绝全闭 IK。
诊断确认只有每个夹爪内的 `left_support_link ↔ right_support_link` 接触；0.01 开度就恢复有效。
Swiftpicker SRDF 现在仅新增这 **两对预期接触**，未关闭夹爪与手臂、另一只手或环境的碰撞检查。
先前整段源数据最小开度约 0.16，已在没有这两项豁免时通过；全闭端点另行补测，不混用两项实验。

## 2. 为什么不能只补两个关节命令？

Swiftpicker 开合时指尖不只横向运动，其纵向位置也变。沿用开启时的固定工具偏置，
会使“法兰正确、实际指尖 EEF 却偏移”，与前面的 EEF 要求矛盾。

```text
法兰到指尖中点的纵向距离：
开启（归一化 1，机械 q=0）：约 212.006 mm
闭合（归一化 0，机械 q=-0.91）：约 229.437 mm
差异：约 17.431 mm
```

本次同时修改：

1. **IK**：根据目标开度、URDF 连杆变换重算法兰→夹爪 EEF，再换算法兰目标。
2. **实测 FK**：使用实际关节反馈重算两指尖中点，不假设被动连杆永远零误差。
3. **TF**：`gripper_l_eef/r` 由静态改为随实测开度更新的动态 TF。
4. **路径检查**：开合状态纳入 MoveIt RobotState，自碰撞检查覆盖开合过程，不是解完手臂再偷偷改夹爪。
5. **限速与采样**：夹爪纳入重定时、命令步长限制；增加开度插值误差超过 0.02 的关键帧。

EEF 轴仍为 `camera_side_up_v2`：+X 指尖方向、+Z 腕部相机侧，未再次旋转工具轴。
本段从 215 增为 **228 个双手联合目标**；旧转换文件继续可读，运行时补采样，不覆盖原始数据。
本轮沿用保守的 0.3 rad/s、0.5 rad/s² 限制，所以在线执行明显慢于源视频；四分屏重定时后仍为 41.67 秒。

## 3. Web 为什么之前不能点击/拖动？

| 打开的内容 | 能否控制仿真 |
|---|---|
| `episode-000-v3/index.html` 中的 Web 截图 | 不能，它是 PNG；MP4 也不能改变三维视角 |
| 用 `file://` 打开 `live_view.html` | 不能，本地文件不是运行中的 ROS/HTTP 服务 |
| 启动服务后打开 `http://127.0.0.1:8765` | 可以，需等三路相机就绪 |

上一轮结束时我清理了后端，地址不会自动保持在线。未得到你的地址栏信息，不能断言你遇到的具体是哪种情况。
旧在线页还未禁止 `<img>` 原生拖拽，可能产生拖图片/拖拽取消，干扰相机 Pointer Events。
现在显式设置 `draggable=false`、禁止原生 dragstart、处理 pointer capture 丢失；图像刷新不替换 DOM 节点。

其他改进：离线明确提示并禁用失效按钮；显示“后端已处理 N 次操作”；提供重置外部视角按钮；
仿真/MoveIt 启动即退出时报告日志位置，不继续打开永远等不到相机的界面。
不能把 HTTP 入队响应当成机器人已执行，因此本轮追加了真实浏览器输入验收。

## 4. 一条命令启动真正的在线页面

在仓库根目录、已下载并转换 episode 0 的前提下：

```bash
mamba activate xense-wbc
export OMNI_KIT_ACCEPT_EULA=YES
bash wbc_demo/run.sh umi-web
```

再打开 **http://127.0.0.1:8765**，不是本地 HTML 或截图。
`umi-web` 自动生成新场景和会话目录；端口占用时拒绝再启动后端。
其他数据段/配置使用 [高级 umi-live 命令](ONLINE_IK_AND_VIEWS_ZH.md)。
左上按钮开始完整预检＋播放；暂停/继续仅在相应阶段启用。
下方 A/B 镜头左键拖动、滚轮缩放；查看操作计数确认后端收到了输入。

## 5. 怎么验收，而不是只调用 API？

`tests/browser_acceptance.py` 通过 Firefox WebDriver BiDi 的 **真实鼠标/滚轮输入**，依次验证：
拖动 A、缩放 B、点击重置、点击播放、点击暂停、检查相位冻结、点击继续并等待整段完成。
不是 `element.click()`、合成 DOM 事件或直接 curl 替代按钮验收。
自动化使用独立 profile；`websockets` 只是 QA 依赖，不是用户使用 Web 的前提。

`tests/gripper_acceptance.py` 还在仿真中检查 0、0.5、1 三个端点，保持指尖 EEF 目标不变。
必须显式传 `--execute`，并且只能在回放控制器退出后执行。
验收图、视频与指标放在 `media/episode-000-v4/`，旧 v3 不覆盖。
当前仍是空场景运动测试，不代表物体接触或真实抓取成功。

最新实测、视频、图片和哈希见 **[episode-000-v4](media/episode-000-v4/README.md)**，
可直接打开其中 `index.html`；保持扁平布局，视频也随目录保存。228/228 与回家通过，0/0.5/1 端点补测通过。
