# 全身 IK、腰部约束与 Web 四视角：给 VLA 工程师的说明

**v4：[开合映射、动态 TCP、浏览器交互修复](GRIPPER_AND_WEB_FIX_ZH.md)**。
快速启动：`mamba activate xense-wbc`，接受 EULA 后运行 `bash wbc_demo/run.sh umi-web`，打开 `http://127.0.0.1:8765`。

本页回答：为什么用 BioIK、±0.5° 是否合理、如何在线拖动视角、四分屏怎样对齐。
最新验收数据和视频见 [四视角验收记录](MULTIVIEW_RESULTS_ZH.md)。此前 v2 是另一轮实际运行，保留作历史对照。

## 1. 先用“端着托盘”理解全身 IK

你告诉机器人：“两只手扶住托盘，两手位置和朝向都别错。”这给的是 **EEF 目标**，不是关节角。

- **FK（正运动学）**：给定肩、肘、腕、腰的角度，计算两只夹爪现在在哪里、朝哪里。
- **IK（逆运动学）**：给定两只夹爪应该在哪里、朝哪里，反过来找一组关节角。
- **全身 IK**：两只手一起求解，同时允许共享的腰部参与，不是两个单臂 IK 各自解完再拼接。

托盘往前放：可以伸肘，也可以弯腰，或者两者一起做。两手目标相同，身体姿态却可能很不同。
腰往右转会同时改变左右肩的位置；因此“左臂先解、右臂再解”容易互相抢同一个腰部。

本实验固定底盘、固定头部，求解组 `wbc_fixed_headless` 包含腰部 5 个、双臂各 7 个关节变量。
双手各有 3 维位置 + 3 维朝向目标，共 12 维任务。19 个变量不等于任意多余角度都可自由选：
限位、机构耦合、自碰撞也会限制可用解，但通常仍有多组姿态满足双手目标。

可把求解器想成在做：

```text
优先满足：左、右夹爪 EEF 位姿，模型限位及机构约束
同时偏好：别突然换姿势，腰不要无故侧倾
外层检查：碰撞、EEF 误差、关节连续性、插值路径和实际反馈
```

上面是理解用的分层，不意味着求解器自动实现了严格优先级优化。
数值优化内部的加权目标不能冒充最终的硬约束；本实现还要检查返回状态与实际运动。

### IK 不等于动力学 WBC

IK 回答“摆成什么姿态”，不计算“每个电机该出多少力矩、接触力如何分配、是否会翻倒”。
本实验由 PhysX 中的关节驱动跟踪位置命令，底盘焊接固定；**不是动态平衡、接触力或力矩级 WBC**。
先学 FK、EEF 坐标、双手 IK、冗余与约束很合适，之后再学 Jacobian、速度级 IK、动力学与接触控制。

## 2. 现在到底调用谁？

```text
UMI 原始 EEF → 共享世界变换 → G2 夹爪 EEF 目标
    → 固定 TCP 变换的逆：换算为模型法兰目标
    → MoveIt 2 /compute_ik 服务
    → genie_sim_moveit_plugins/BioIKPlugin 插件名
    → 本仓库 vendored GenieBioIK 扩展 + BioIK 求解器
    → 候选关节角 + FK/碰撞/限位/路径检查
    → /joint_command → PhysX 执行 → 关节反馈 → 夹爪 EEF 误差
```

**MoveIt 2 是框架，不是一个具体 IK 算法。** 它管理机器人模型、规划组、运动学服务和碰撞场景，
通过插件接口选择某个 IK 求解器；配置里的 `kinematics_solver` 就是这个选择。
参见 [MoveIt 运动学配置说明](https://moveit.picknik.ai/main/doc/examples/kinematics_configuration/kinematics_configuration_tutorial.html)。

**BioIK 是第三方数值 IK 求解器及 MoveIt 插件。** 它支持多个末端目标、额外目标及权重；
不是智元专有 IK SDK，也不是 Pinocchio。
参见 [BioIK 项目与目标说明](https://github.com/TAMS-Group/bio_ik)。

**GenieBioIK 是本仓库的适配/扩展类。** 它把该模型的机构耦合、靠近 seed 的偏好、姿态目标等
接到 BioIK 上，让通用求解器按这里的机器人模型工作。它不是另一个完整的动力学控制器。
配置见 `source/geniesim_ros/src/ros_ws/src/genie_sim_moveit/config/kinematics.yaml`；
实际实现还包括 `external/bio_ik/src/kinematics_plugin.cpp` 中 `genie_sim_moveit_plugins::BioIKPlugin` 的扩展。

这里有容易误读的地方：**插件名的包路径不等于运行时实际加载的库路径**。
此前已核查当前环境实际加载 `devel/lib/libbio_ik.so`，不是仅凭 YAML 名称下结论。

### 为什么选它：原则而非“最强算法”排名

1. **先复用仓库已经接好的接口**：MoveIt、双末端规划组、G2 机构约束已存在，避免同时更换模型和求解器。
2. **双手与共享腰一起求解**：这里确实需要多目标和冗余姿态偏好，而不只是单臂解析 IK。
3. **可审计**：代码、参数、加载库、返回解和实际反馈都能核查；发现旧直腰参数未生效后已修复参数命名空间。
4. **用误差和失败说话**：不是看到动画就认为 IK 正确；先全段预检，再执行、记录实际 EEF 和底盘漂移。

我没有做 BioIK 与其他库的同预算基准测试，所以不宣称它最快、最稳或最适合所有 VLA。
它也不是已验证的 100 Hz 在线求解方案。以后若需要随反馈每周期更新目标，应另外评估求解时间、连续性、
不可达处理与安全约束，而不能简单把本次预检代码塞进实时循环。

## 3. roll ±0.5° 合理吗？

**作为“端平托盘、限制侧倾”的任务约束可以合理；作为全身 IK 的普适要求不合理。**

roll 在这里是 `idx04_body_joint4` 绕局部 X 轴侧倾。模型原生限位约 ±25.58°，不是 ±0.5°。
底盘已经固定，不存在“为防摔必须侧倾不足半度”的结论。

| 策略 | 通俗解释 | 优点与代价 |
|---|---|---|
| `soft`（Web 默认） | 尽量站直，但确有需要时允许侧倾 | 少无谓动作，保留更多可达空间；不保证半度内 |
| `upright` | 这次任务只接受计划 roll 在 ±0.5° 内 | 适合直腰对照实验；缩小可行域，可能更难求解或失败 |
| 旧 CLI 的 `config` | 沿用 JSON 中设置 | 兼容旧实验，当前默认 JSON 含 ±0.5°；不要与 Web 默认混淆 |

两种 Web 策略都保留当前 roll 零位软偏好，权重 5.0；`soft` 只移除额外的半度硬范围。
腰部其他自由度和双臂仍参与求解，**不是把整个腰锁死**。

半度硬约束用在 IK 请求及返回状态检查中，不是解完后把 roll 数值强行清零。
后者会破坏双手位姿，就像扶着托盘时突然掰直腰，手的位置也会变。
此外，**计划限位不等于实际跟踪零误差**：动力学、驱动和采样使实际角度略有偏差，要单独测量。

直腰不是唯一审美标准。比如左右手目标高度差很大时，侧倾可能减少手臂极限姿态；
这时应根据任务选择软偏好、硬范围或接受合理侧倾，不应为了画面好看无限加权。
单次随机数值搜索失败，也不能证明目标数学上一定不可达。

## 4. 四个视图怎样对应？

```text
┌─────────────────────────┬────────────────────────────┐
│ 原始 UMI head_left      │ 虚拟 UMI 头部同向视角      │
│ 数据集原视频，不翻转    │ 当前机器人实际仿真画面    │
├─────────────────────────┼────────────────────────────┤
│ 外部 A，可拖动/缩放     │ 外部 B，可拖动/缩放        │
│ 查看腰、肩、腕相对位置  │ 从另一侧看遮挡与姿态       │
└─────────────────────────┴────────────────────────────┘
```

以前用外部侧面镜头与头显俯视直接比较，当然会有观察方向混乱；左右手在画面中左右也不等于世界坐标左右。
现在右上视角取 **原始数据中的 `head` 位姿**，与双手使用同一个源 world → `odom` 变换，
随同一个源相位移动相机。头部 +X 朝前、+Y 朝左、+Z 朝上，转换到 USD 相机 -Z 朝前、+Y 为画面上方。
不靠翻转图片、手调某一帧朝向或交换左右手来对齐。

轴向依据是保存的导出源码 `logs/umi-research/source-evidence/taccap-mcap-lib.rs` 中 world/head 定义及
`pico_pose_to_world` 的旋转共轭，6D 编码见 `bi_taccap.rs`；不是仅凭头显品牌猜测相机 optical frame。
生成的相机审计保存轨迹、源哈希、世界变换和配置；启动时检查 scene 哈希及回放配置一致。

**这是虚拟头部同向视角，不是标定后的 G2 头部相机，也不是逐像素复现 UMI 光学成像。**
公开数据未提供本段 `head_left` 可核查的相机内外参，当前虚拟镜头使用明确记录的 640×480、fx=fy=380。
所以可以比较观看方向与动作顺序，不能据此声称视野、畸变、相机中心或投影误差完全一致。
机器人实体头部关节没有跟着源头部旋转；我们移动的是虚拟观察镜头。

### 黑屏排查为什么重要

当前 AS3 模型发布的是各 link 相对父节点的渲染变换；物理引擎另外在机器人根节点应用了
`init_base_pose = (-0.25, 0, 0.04)`。独立渲染器未应用这项根偏置时，机器人显示位置与 `odom` 不一致，
按正确世界坐标放置的近身镜头反而进入了显示网格内部。

诊断只改变渲染根变换，不改变物理关节：黑屏变成了可见的夹爪/地面，确认了机制。
现在 Web 渲染桥补齐场景规定的固定根位姿。生成器要求底盘焊接固定；**不适用于移动底盘直接照搬**。
没有把相机挪到好看的任意位置，也没有改物理模型来隐藏问题。

## 5. 在线回放与在线 IK 是不同的“在线”

现在可以在线查看、暂停、恢复、停止、拖动外部镜头：机器人在运行中的 PhysX 中运动，不是播放器播旧 MP4。
浏览器显示原生渲染图像，拖动只更新渲染相机，不向关节发送运动命令。

但求解流程仍是：**先完整预检 215 个双手联合目标，再在线执行已检查的关节轨迹**。
不是每个控制周期根据新手势或环境变化重新解 IK。源 UMI 也是已录制数据，不是直播遥操作输入。
这是为了保留已验证的碰撞/路径/误差检查，没有用“在线”一词掩盖离线求解。

在线执行受速度/加速度约束而慢于源视频，左上源帧随机器人源相位推进；暂停时源相位也冻结。
完成后可生成源时长的四分屏视频：按 ROS 图像时间、命令源相位重采样，**不是机器人原速**。
三路机器人画面先要求同一个图像时间戳再组合；源相位差和渲染时间差仍要报告，不能叫严格硬件同步。

## 6. 如何启动 Web 交互

在仓库根目录执行；假定数据与转换结果已在本机、ROS 已构建、你已接受 Omniverse EULA：

```bash
mamba activate xense-wbc
export OMNI_KIT_ACCEPT_EULA=YES
tag=$(date +%Y%m%d-%H%M%S)
python wbc_demo/umi_demo.py view-scene \
  --input wbc_demo/data/converted/episode-000.json \
  --output "wbc_demo/logs/scene-umi-web-${tag}.yaml"
WBC_SCENE="logs/scene-umi-web-${tag}.yaml" bash wbc_demo/run.sh umi-live \
  --input wbc_demo/data/converted/episode-000.json \
  --scene "wbc_demo/logs/scene-umi-web-${tag}.yaml" \
  --output "wbc_demo/logs/umi-web-${tag}"
```

浏览器打开 `http://127.0.0.1:8765`。等“三相机就绪”，选择策略，点“预检＋播放”。
首次需要等完整预检；拖动下方两个镜头，滚轮缩放。右上镜头自动跟随源头部方向，不能拖动。
播放阶段的“暂停/恢复”保持最后关节目标并冻结相位；**靠近首帧/回家阶段不支持暂停**，可用“停止”。
停止后保持当前位置；“关闭本次会话”或终端 Ctrl+C 清理这次启动的控制器与后端，不结束其他用户进程。
完成后页面可保留查看或重新播放；每次播放使用独立 `run-NNN` 和 `recording-NNN`。

默认是本机专用：只监听 loopback，并检查 Host/Origin；不要把端口直接暴露到公网。
Web 页是本地 HTML/JS，无 PyQt/PySide、无 CDN；后端使用 Python 标准库 HTTP + ROS。
三维渲染仍用仓库原生 OVRTX，非浏览器重画的 FK 示意图；默认不额外启动 RViz。

### 原始记录的位置

- `run-NNN/report.json`、`joint_plan.json`：求解、策略、限位、执行/回家及来源证据。
- `run-NNN/tracking.csv`、`command_phase.csv`：实际关节/EEF 与命令源相位。
- `recording-NNN/views.mp4`、`frames.csv`、`metadata.json`：三路同时间戳仿真画面与逐帧来源。
- `session.json`：播放、暂停、恢复、停止、相机拖动等用户事件。
- 单独的 `umi-backend-*/`：仿真/MoveIt/在线查看日志，控制器退出后仍保留。

当前只完成 episode 0 的机器人实际回放验收；没复现物体接触/抓取，夹爪已按 0 闭合 / 1 开启回放。
可达性不是任务成功率，也不等于硬件控制安全认证。
