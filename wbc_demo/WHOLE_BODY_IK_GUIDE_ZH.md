# 给 VLA 工程师的全身 IK 入门：从固定双臂到会弯腰的机器人

> 阅读对象：用过固定支架双臂，第一次接触带腰部、轮式底盘的机器人。
>
> 先记住一句话：**全身 IK 是让多个身体部位共同配合，找到满足任务目标的一组关节姿态。**
>
> 本文也解释：本次 demo 的来源、运行命令、独立工作目录、代码同步方法，以及下一步做什么。

## 1. 先纠正两个容易混淆的地方

### 1.1 “全身”不等于每个关节都必须动

把脚钉在地上的人，也可以弯腰、转身、伸出双手去拿东西。
机器人同理：底盘固定，但腰部和双臂一起求解，仍然可以称为固定底盘全身 IK。

更准确的名字是：**固定底盘的双臂 + 躯干联合逆运动学**。
这里的“全身”强调联合考虑，不意味着必须包含头部、夹爪、底盘或双腿。

### 1.2 IK 与 WBC 不是两个互不相干的领域

- **IK 是一种求解问题**：给定手等任务部位的目标，反推关节应该怎么摆。
- **WBC 是协调全身运动/受力的控制框架**：根据多个任务和约束，持续产生控制指令。
- WBC 可以使用 IK，也可以使用逆动力学；广义的 WBC 不一定输出力矩。

因此，“先掌握全身 IK，再学习动力学 WBC”是适合你的学习路线，
不是说必须完整学完一个独立领域才能碰另一个领域。

本次跑通的是 **全身位姿 IK + 关节位置控制**，不是接触力分配或力矩级动力学 WBC。
仓库中的文件名 `wbc.launch.py` 也不能单独证明它运行了动力学 WBC。

## 2. 从你熟悉的固定双臂理解

### 2.1 固定双臂：只有手臂可以帮忙

想象你坐在椅子上，背部被绑住，面前有一个杯子。
你只能调整肩、肘、腕；如果杯子超出手臂可达范围，再聪明的手臂 IK 也够不着。

这是你熟悉的固定支架平台：手臂根部相对于世界不动。

### 2.2 加入腰部：身体也可以帮忙

现在解开背部，但椅子仍固定。
你可以前倾一点，把肩膀送过去，再配合肘和腕保持杯口朝上。

新增的腰部关节不仅改变“腰的姿态”，还会改变两只手臂根部的位置和方向。
所以手的世界位姿由两部分共同决定：

```text
世界中的手 = 世界中的底盘 × 腰部变换 × 手臂变换 × 工具变换
```

这里的“×”是坐标变换的复合，不是把几个位置坐标直接相加。

### 2.3 两只手为什么不能各算各的？

想象双手端着一只托盘。右手想往前够，左手还要托住另一端。

如果右手 IK 让腰前倾，左手的肩膀也跟着动；左手原来的 IK 解就可能失效。
腰是两条运动链共享的变量，不能由两个互不沟通的求解器随意决定。

全身 IK 的做法是：**把共享腰部和两条手臂放进同一个问题，一起满足左右手目标。**

如果腰部始终固定，左右手分别求 IK 在一些任务中可以工作；
但仍需要额外处理双臂碰撞、相对位姿等耦合要求。

## 3. FK 和 IK：一个算结果，一个找原因

### 3.1 正运动学 FK

输入：所有相关关节角度 `q`。
输出：手的位置和朝向 `T`。

```text
肩膀转多少、肘弯多少、手腕转多少 → 手最后在哪里、朝哪儿
```

记作 `T = FK(q)`。

### 3.2 逆运动学 IK

输入：手要到达的目标位姿 `T_target`。
输出：一组关节角度 `q_target`，使 `FK(q_target)` 尽量满足目标。

```text
手要到杯子旁边，并且夹爪竖直 → 肩、肘、腕、腰应该怎么摆
```

注意，“位姿”包含**位置 + 朝向**。让手到一个点，与让手到这个点并保持杯口朝上，
是两个难度不同的问题。

### 3.3 一个能手算的例子

假设有一条二维两节机械臂，每节长 30 cm：

```text
x = 0.3 cos(q1) + 0.3 cos(q1 + q2)
y = 0.3 sin(q1) + 0.3 sin(q1 + q2)
```

- `q1 = 0°，q2 = 90°`：手到 `(0.3, 0.3)` 米。
- `q1 = 90°，q2 = -90°`：手也到 `(0.3, 0.3)` 米。

同一个手的位置，至少有两种关节摆法。这叫**多解**。
这个例子只要求位置；两种解的末端朝向不相同。

如果目标是 `(1.0, 0.0)` 米，而肩膀不能移动，总臂长只有 0.6 米，就无解。
“换一个更好的优化器”不能突破这个几何事实；增加腰部或移动底盘才可能改变可达范围。

## 4. 本次 G2 问题到底有多大？

选用仓库已有的 `wbc_fixed_headless` 规划组：

| 部位 | 参与 IK 的变量数 |
|---|---:|
| body/腰部关节 | 5 |
| 左臂 | 7 |
| 右臂 | 7 |
| 合计 | **19** |
| 底盘、头部、夹爪 | 不作为这个 IK 问题的可变关节 |

`headless` 在这里指**不把头部纳入求解**。
而启动参数 `headless:=true` 指**Isaac 不开原生 GUI**；这是另一回事，RViz 仍然可以打开。

两只手各有 3 个位置 + 3 个朝向目标，合起来最多有 12 个独立任务约束。
在局部非奇异、约束独立且没有其他限制时，可以用 `19 - 12 = 7` 直观理解冗余空间。
这不保证总有解，也不代表实际任何姿态下都有 7 个可自由运动的方向。
关节限位、碰撞、机械耦合、奇异位形都会改变情况。

**冗余的价值：同样把双手放到指定位置，可以少弯腰、少抬肘、远离限位，或离当前姿态更近。**

**冗余的代价：不加偏好或连续性处理，就可能每次找到不同的身体姿态。**
所以“双手回到起点”不等于“19 个关节都回到起点”；本 demo 也没有保证后者。

## 5. 求解器到底在“优化”什么？

先用不带复杂符号的方式理解：求解器不断试关节姿态，让下面的总分变小。

```text
总分 = 左手位置/朝向误差
     + 右手位置/朝向误差
     + 可选的姿态偏好代价
     + 可选的远离当前关节姿态的代价
```

同时要求关节不越界，并用适当机制排除碰撞等无效解。

姿态偏好可以是：腰尽量直、关节不要贴近限位、不要突然从肘上解跳到肘下解。
这些偏好不一定都要加入，也不一定都能用同一种求解器配置实现。

这里是**概念示意**，不是本仓库 BioIK 实现的逐字目标函数，
也不声称上述所有偏好都已经在当前 demo 中启用并验证。

### 5.1 软偏好与硬约束不一样

- “底盘尽量少动”：可以是软代价，必要时求解器仍可能选择移动。
- “底盘绝不能动”：应该排除底盘变量，或施加对应硬约束。

本 demo 同时做了两层限制：

1. IK 组不包含底盘变量。
2. 仿真模型设置 `pin_base_to_world: true`，物理上把底盘固定到世界。

此外，脚本监测底盘 TF 漂移，而不是只看到代码没发底盘命令就认定底盘没动。

### 5.2 加权与任务优先级不一样

如果“手到目标”和“腰保持直立”只是加权相加，两者可能互相让步。
严格任务优先级则要求：满足更重要任务后，才利用剩余自由度处理次要任务。

例如双手端热汤：不能为了“腰更直”而破坏“托盘不倾斜”。
这是后续学习分层 IK / 分层控制时要理解的问题，不是把某个权重调大就一定解决。

## 6. 雅可比矩阵：身体各关节能帮手移动多少？

把关节变化想成一排旋钮。
雅可比矩阵 `J` 描述：**每个旋钮轻轻拧一点，手的位置/朝向会怎样变化。**

局部近似是：

```text
任务空间的小变化 ≈ J × 关节的小变化
```

对本次双手完整位姿任务，常见局部表示中的 `J` 是 `12 × 19`。
腰部对应的列通常同时影响左右手；左臂关节不会直接改变右手的 FK，右臂同理。

这就解释了为什么要联合求解：共享腰部的一个变化，会同时出现在两只手的误差里。

### 6.1 位姿 IK 与微分 IK

- **位姿 IK**：给一个目标，求一组目标关节角度。
- **微分 IK**：根据当前误差和雅可比，每个周期求一个小的关节增量或关节速度。

当前 demo 在每个目标点调用现成位姿 IK，再插值执行。
它不是我新写的雅可比 QP 求解器，也不是持续在线的微分 IK 控制器。

### 6.2 奇异位形的直觉

手臂完全伸直时，你希望手继续沿手臂方向往外伸，关节很难再提供这个方向的运动。
附近还可能出现“手只移动一点，却需要关节转很多”的情况。

微分 IK 常用阻尼、速度限制、避奇异目标等方式改善行为。
但阻尼不是魔法：它往往在任务精度和关节变化幅度之间做取舍，不能让不可达目标变可达。

## 7. 四件事情分开看：IK、路径、跟踪、动力学

用“端着一杯水走到桌边”来区分：

| 层次 | 回答的问题 | 常见输出 |
|---|---|---|
| IK | 到桌边时身体应该摆成什么姿态？ | 目标关节位置 |
| 运动规划 | 中途怎么绕开桌角和自己的身体？ | 路径/轨迹 |
| 运动跟踪 | 当前没到目标，下一步应该如何纠正？ | 位置、速度或力矩指令，取决于接口 |
| 动力学 WBC | 手拿着负载、脚/轮接触地面时，如何协调运动与受力？ | 常见为加速度、接触力、关节力矩等 |

**找到一个无碰撞的终点，不代表到终点的路径也无碰撞。**
**规划出一条几何路径，也不代表真实电机一定跟得上。**
**把姿态算对，也不代表承重时不会倾覆或失去接触。**

动力学 WBC 会进一步考虑质量、惯量、重力、驱动力矩、接触与摩擦等。
广义 WBC 也包含基于运动学的协调控制，不能简单定义成“WBC 必须输出力矩”。
可参考 Nori 等人的 iCub 力调节原始研究：其系统包含任务空间逆动力学、
关节力矩控制和接触力估计；这是比本 demo 更进一步的控制问题。

对你当前的固定底盘、自由空间双臂任务，先把 IK、连续性和运动跟踪学明白很划算，
不需要一开始就同时解决双足平衡和接触力优化。

## 8. 那三行命令逐行解释

**升级说明：现在 `all` 默认运行 9 类大范围压力测试，`lab` 启动交互实验台。
本节中的四点小范围序列保留为 `demo` 子命令；最新操作见 [LAB_USAGE.md](LAB_USAGE.md)。**

从本 worktree 根目录运行：

```bash
mamba activate xense-wbc
export OMNI_KIT_ACCEPT_EULA=YES
bash wbc_demo/run.sh all --cycles 3
```

### 第一行：切换已经安装好的环境

选择 Python、ROS 2、MoveIt、Isaac Sim 等依赖所在的 `xense-wbc` 环境。
它不是重新创建环境，也没有开始运动。

### 第二行：为当前 shell 的子进程传递许可证确认

设置 Isaac/Kit 启动所需的 EULA 接受标志。只有同意对应协议才应设置。
它不是机器人控制开关，也不负责安装软件。

### 第三行：运行我新增的一键编排脚本

`all` 表示把三个部分一起启动；`--cycles 3` 传给我写的运动脚本，表示运行三轮。

```text
run.sh all
  ├─ 仓库已有的 app.launch.py
  │    └─ 加载 G2 / GDK 场景，固定底盘，启动 PhysX 与 OVRTX
  ├─ 仓库已有的 wbc.launch.py
  │    └─ 启动 MoveIt、关节状态桥和 RViz
  └─ 我新增的 experiments.py / lab_core.py（初版为 dual_arm_ik.py）
       └─ 设置双手目标 → 调用 MoveIt IK → 检查 → 发送关节指令 → 记录实测结果
```

关键参数：

- `headless:=true`：不打开 Isaac 原生窗口，仿真仍真实计算；RViz 是独立窗口。
- `use_ros2_control:=false`：此 demo 不由 ros2_control 执行轨迹，避免和脚本争抢控制。
- `/joint_command`：脚本向仿真发送腰部 + 双臂的关节位置目标。
- `/joint_states`：仿真反馈实际关节状态；桥接后提供给 MoveIt 和测试脚本。
- `/compute_ik`、`/compute_fk`：由现成 MoveIt 服务求逆运动学、验证正运动学。

**不是把手的位姿直接写入仿真，也不是直接瞬移机器人。**
IK 算出关节目标，脚本发布平滑插值的关节位置指令，PhysX 中的关节驱动再实际跟踪。
但是底层用的是位置驱动/PD，不是本脚本实现的动力学 WBC。

### 初版经典回归每轮具体做什么？

这一小节只对应 `bash wbc_demo/run.sh demo --cycles 3`，需要后端已经运行。
当前 `all --cycles 3` 则运行 27 个大范围目标，并在每个目标后回初始关节姿态。

启动后读取当时的双手位姿作为参考，保持两手目标朝向不变：

| 每轮目标 | 左右手相对于启动参考位姿的平移 |
|---|---|
| 1 | `x + 8 cm，z - 8 cm` |
| 2 | `x + 16 cm，z - 16 cm` |
| 3 | `x + 8 cm，z - 8 cm` |
| 4 | 回到参考位置 |

这些是 `odom` 世界坐标系的方向，不是每次相对上一目标再累加。
初始底盘航向为零时，可以直观理解成双手一起向前/向下，再返回。
因此三轮是 **12 个双手联合目标**，不是 3 次抓取，也不是 12 个单手目标。

默认每段插值约 4 秒，随后保持目标约 2 秒，另加 IK 和检查耗时。
执行前对每段关节空间路径取 21 个样本检查有效性。
通过后窗口保持打开，按 Ctrl+C 清理这次脚本创建的进程组。

### 这个演示没有做什么？

- 没有运行 VLA、视觉识别、语言理解、策略训练或抓取规划。
- 没有夹紧瓶子或验证托盘搬运；双手只是执行预设的位姿目标。
- 没有保证 TCP 中途走严格直线；插值在关节空间进行。
- 没有把 GDK 货架自动同步为 MoveIt 障碍物；离散自碰撞检查不等于完整环境避障。
- 没有保证完整双手相对位姿在运动中严格不变；即使终点满足，也不能据此宣称能端刚性托盘。
- 没有连接真机；RViz 的 Execute 没有接执行控制器。
- 没有因为模型名或文件名带 `wbc` 就宣称已实现动力学 WBC。

| 指标 | 含义 | 本次最终三轮 |
|---|---|---:|
| IK 残差 | 对算出的目标关节做 FK，离目标手位姿多远 | 位置最大 2.83 微米 |
| 仿真跟踪误差 | 对仿真反馈关节做 FK，离目标手位姿多远 | 位置 3.43–7.90 mm |
| 腰部运动 | body 关节相对运行起点的变化 | 最大单关节约 0.418 rad |
| 底盘漂移 | 运行期间底盘 TF 相对起点的变化 | 三维位置最大约 4.03 微米 |

第一行小，不代表第二行也一样小：
**IK 答案算得准，与物理系统能否准确执行，是两件事。**

这些测试证明这组目标可以求解和执行，不证明所有目标都可达、姿态最优、实时性足够或真机安全。
TCP 的“实测”来自仿真关节反馈 + URDF FK，不是外部视觉测量或 USD mesh 的独立测量。

本 demo 把 `arm_l_end_link` / `arm_r_end_link` 当作任务末端。
接真实夹爪时，还要核对它们与真正抓取 TCP 的固定工具变换，不能自动认为是同一个点。

## 11. 初次复现为何使用独立 worktree？（历史记录）

**2026-10-13 更新：按操作者要求，代码和运行环境已迁回 `xense-genie_sim`。
旧 worktree 和原目录快照已归档备份。以下小节是迁移前的背景与操作建议，
不是当前目录状态；现在的同步与运行步骤请看 [MIGRATION.md](MIGRATION.md)。**

不是因为原目录的名字不能用，而是为了不破坏原目录的 Git 状态。

本次检查发现原目录：

- `HEAD` 在 `main` 的 `6ca11c7`。
- 索引中没有受跟踪条目，`git diff --cached` 显示 **5721 个暂存删除项**。
- 这描述的是 Git 索引相对提交的状态，不等于磁盘上的 5721 个文件全都消失了。

在不知道这些暂存删除是否是你有意操作之前，直接 reset、覆盖文件或提交都不合适。
所以我创建了同一提交的独立 **Git worktree**。

```text
同一个 Git 仓库 / 同一个 origin
  ├─ xense-genie_sim       ：原工作目录，保留其索引与文件状态
  └─ xense-genie_sim-demo  ：独立工作目录，用于配置、修补、运行和记录
```

像一本书摆在两张桌子上：共用提交历史和远端，但工作文件、索引、HEAD 可以独立。
它不是脱离私人仓库的新项目，也不是只能往智元官方仓库推送的副本。

当前两个目录的 `origin` 都是你给出的私人仓库：
`https://github.com/FZAbiding/xense-genie_sim.git`。
demo worktree 当前是 detached HEAD；**我没有创建分支、提交或推送。**

### 11.1 后续同步到私人仓库：推荐从 demo worktree 提交

不必先把文件拷回原目录。可以直接在 demo worktree 创建功能分支并推到同一个 origin。

然后在私人仓库创建 Pull Request 合入目标分支。若同名功能分支已存在，先检查它，

### 11.2 哪些东西不会跟着 push？

默认会纳入版本控制的是源码、配置和说明文档，不是整台机器的安装状态。

| 内容 | 随上述源码提交上传？ |
|---|---|
| demo 脚本、兼容补丁、教学与结果说明 | 是 |
| `xense-wbc` 虚拟环境 | 否 |
| `devel/`、`devel_build/` 等构建产物 | 否，已忽略 |
| assets 数据集、运行生成的 USD 场景 | 否，已忽略 |
| `logs/` 下视频、CSV、JSON、环境快照 | 否，已忽略 |
| 原本已经受 Git LFS 管理的机器人模型 | 继续遵循仓库已有的 LFS 管理方式 |

想在远端保存运行证据，可以挑选小的报告和视频附件单独归档，
或上传到有权限的制品存储，不要把整个环境、29 GB 数据集或所有编译产物塞进 Git。
资源的上游许可也需要遵守，私人仓库不等于可以忽略资源许可。

当前 editable 安装和 ROS 构建路径指向 demo worktree。
**代码 push 完，不代表可以立刻删除这个目录。**
如果以后要只保留原目录，应先确认并处理原目录的索引状态，再迁移代码，
重新绑定 editable 包、资产路径并构建验证；不要直接拷贝带旧绝对路径的构建产物。

## 12. 下一阶段：先做一个“为什么需要腰”的实验

### 阶段 A：固定底盘交互式全身 IK + 腰部锁定/解锁对照

**这一阶段现已实现**，运行 `bash wbc_demo/run.sh lab` 即可体验。
仍然不解锁底盘，不进入双足平衡，也不训练 VLA。操作与边界见 [LAB_USAGE.md](LAB_USAGE.md)。

具体交付：

1. 能交互设置左右手目标；拖动目标时，有受限速保护的执行开关，而不只是 RViz 的 Plan 显示。
2. 同一目标对比 `wbc_fixed_arms`（仅双臂、固定腰）与 `wbc_fixed_headless`（腰部 + 双臂）。
3. 显示两手目标/实际轨迹、各腰部关节角度、误差和求解耗时。
4. 选择并验证“仅双臂失败、加入腰部后成功”的目标；不预先假定某个厘米数一定构成这种案例。
5. 加入可识别的失败反馈：不可达、碰撞、限位、超时、关节状态停止，而不是失败后突然跳姿态。

验收标准：你能亲手看到腰如何改变双臂可达域，并能解释失败原因。
同时确认交互执行过程中关节速度与连续性受控；不能把 marker 突然拖远后直接下发跳变关节目标。

这里的 `wbc_fixed_arms` 和 `wbc_fixed_headless` 都是仓库已有组；
自动 A/B、交互执行、速度重定时、路径检查和软件停止已经加入，
具体通过了哪些测试以 `EXPERIMENT_RESULTS.md` 为准，不把仿真保护当成真机安全认证。

### 阶段 B：从“算几个终点”升级到连续协调

增加微分 IK 或合适的连续求解方法，处理关节限位、速度限制、避奇异和解的连续性。
再把货架等障碍物接入规划碰撞世界，增加双手相对位姿任务。

端托盘是好例子：既要整只托盘移动，又要全程保持双手间刚性关系，不能只检查四个终点。
是否需要全局规划、在线避障或分层任务，取决于实际场景，不能仅靠一个 IK 调用解决所有问题。

### 阶段 C：再解锁轮式底盘

加入底盘 `x / y / yaw` 后，可以比较“先弯腰”还是“先靠近目标”。
但底盘可达的位姿与轮子能连续实现的运动不是一回事。
需要接通实际底盘控制链，考虑轮系运动学、转向/速度限制和碰撞；
不能只给规划器一个自由平面关节，就把它当作完整移动操作控制。

### 阶段 D：根据任务决定是否学习动力学 WBC

当目标变成持重、推拉、抗扰动、接触力控制或动态稳定性时，再深入动力学与接触约束。
先核对平台开放的位置/速度/力矩接口与传感器条件，不能默认真机支持任意力矩控制。
固定底盘的自由空间操作不必为了“全身”二字强行上双足控制那套复杂度。

## 13. 怎么与 VLA 接起来？

如果策略输出的是双手任务空间动作，可以把你熟悉的链路扩展为：

```text
图像 / 本体状态 / 语言
        ↓
VLA 输出双手位姿或位姿增量 + 夹爪动作
        ↓
坐标系变换、工具 TCP 定义、动作限幅
        ↓
全身 IK：把手的意图分配给腰与双臂
        ↓
轨迹/限速/安全检查
        ↓
底层控制器 → 机器人 → 反馈
```

如果策略直接输出关节动作，就不一定需要再串一个位姿 IK。
全身关节动作维度、数据分布和安全约束会不同，需要单独设计，而不是机械地把 IK 插进去。

尤其注意：腰动了，躯干/头部相机的世界位姿通常也会变。
原来固定双臂平台上“相机到世界固定”的假设未必还能用。
要结合关节状态更新运动链上的相机外参，并区分世界系、底盘系、相机系和工具系动作。

## 14. 五道自测题

1. 右手想前伸，腰前倾之后，为什么左手不能继续沿用原来的关节解？
2. 双手回到原来的位置和朝向，为什么腰与肘不一定回到原角度？
3. IK 的 FK 残差只有微米，为什么仿真实际跟踪误差还会有毫米？
4. 为什么“底盘移动代价很大”不等于“底盘绝对固定”？
5. 为什么拖动 RViz marker 并看到模型移动，不足以证明 PhysX 机器人执行成功？

答案要点：共享腰部改变两条链；冗余多解；几何求解与物理跟踪分层；软代价不等于硬约束；
目标/规划可视化与实际关节反馈是不同的数据流。

如果这五题都能解释，你就已经具备继续做固定底盘全身 IK 工程实验的基本概念。
